  Data model

  migrations/0001_create_links.sql, applied by wrangler d1 migrations apply 
  --local:

  CREATE TABLE links (
    code       TEXT PRIMARY KEY,
    url        TEXT NOT NULL,
    clicks     INTEGER NOT NULL DEFAULT 0 CHECK (clicks >= 0),
    created_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now'))
  ) STRICT;

  Choice: code is the primary key
  Reasoning: The database itself guarantees codes are unique, which is what
    handles two requests claiming the same code (see failure modes). It's also
    the index the redirect lookup uses. No separate id, because nothing needs
    one.
  ────────────────────────────────────────
  Choice: Click count is a column, not a table of click events
  Reasoning: The requirement is a count. clicks = clicks + 1 in one SQL
  statement
    is atomic in SQLite. A click-events table would be a feature nobody asked
    for.
  ────────────────────────────────────────
  Choice: No unique constraint on url
  Reasoning: Shortening the same URL twice gives two codes, each with its own
    count. Deduplicating would add a lookup and an unclear rule for little
    benefit.
  ────────────────────────────────────────
  Choice: created_at
  Reasoning: Sorts the list newest first.
  ────────────────────────────────────────
  Choice: STRICT
  Reasoning: Rejects wrong column types at the database instead of quietly
    converting them.
  ────────────────────────────────────────
  Choice: Codes are 7 base62 characters
  Reasoning: Generated with crypto.getRandomValues and rejection sampling (bytes

    ≥ 248 are thrown away, so every character is equally likely). That's 62⁷ ≈
    3.5×10¹² possible codes, so collisions are rare but still handled. No custom

    codes, since they weren't asked for.

  API

  The HTML is rendered on the server and uses a plain form, so it works without
  JavaScript and errors come back in the page itself.

  Route: GET /
  Behavior: Page with the create form and a table of every link (code, short
    link, original URL, click count), newest first
  Requirement: 1, 4
  ────────────────────────────────────────
  Route: POST /links (form field url)
  Behavior: Valid: 303 to /?created=<code>, and the page highlights the new
  short
    link. Invalid: 400, the page is re-rendered with the error and the input you

    typed. Storage error: 500 page
  Requirement: 1, 6
  ────────────────────────────────────────
  Route: GET /:code
  Behavior: 302 to the original URL with Cache-Control: no-store, and the count
    goes up. Unknown code: HTML 404 page
  Requirement: 2, 3, 6
  ────────────────────────────────────────
  Route: Anything else
  Behavior: A path that isn't a 7-character code gets a 404 without touching the

    database. A wrong method gets 405
  Requirement: 6

  - Why 302 and not 301: browsers cache a 301, so later clicks would never reach
    the Worker and the count would stop going up.
  - Why 303 after creating a link: reloading the page won't submit the form
    again.
  - No overlap between routes and codes: a code is exactly 7 alphanumeric
    characters, so links (5 characters) can never be mistaken for one.
  - No JSON API: it isn't required, and the tests check the database directly
    instead of parsing HTML. One could be added later in a few lines.

  URL validation (on the server):
  - Trim the input, then parse it with new URL().
  - Only http: and https: are allowed. This blocks javascript: and data: links,
    which are dangerous because the URL is both shown as a link and redirected
    to.
  - The URL must have a hostname and be at most 2048 characters.
  - The stored value is the parsed href, the normalized form.

  HTML escaping: every value that comes from a user (URLs, the echoed input) is
  escaped before it goes into the page.

  - src/index.ts: routing.
  - src/links.ts: validation, code generation and queries.
  - src/views.ts: HTML and escaping.
  - migrations/0001_create_links.sql.

  Failure modes

  Case: The insert fails (D1 throws)
  Behavior: It's a single atomic statement, so nothing is partly saved. The
  error
    is logged and you get a 500 page ("Couldn't save the link, try again"). A
    code is never shown unless its row was saved.
  ────────────────────────────────────────
  Case: Two requests claim the same code at once
  Behavior: INSERT … ON CONFLICT(code) DO NOTHING RETURNING code. D1 handles
    writes one at a time, so exactly one insert wins. The other gets no row
  back,
     picks a new code and retries, up to 5 attempts, then returns 500. There's
  no
     "check if it exists, then insert" step, which would leave a gap for a race.

    INSERT OR REPLACE is ruled out because it would silently overwrite someone
    else's link.
  ────────────────────────────────────────
  Case: Two redirects for the same link at once
  Behavior: UPDATE links SET clicks = clicks + 1 WHERE code = ? RETURNING url
    does the lookup and the increment in one round trip. The count is never read

    into JavaScript and written back, so no click is lost.
  ────────────────────────────────────────
  Case: The redirect query fails
  Behavior: 503 page. It doesn't guess a destination or skip counting. The count

    is updated before the response is sent, not in waitUntil, so it's never lost

    silently. The cost is one query's delay on each redirect.
  ────────────────────────────────────────
  Case: The list query fails
  Behavior: 500 page with a message.
  ────────────────────────────────────────
  Case: Malformed input
  Behavior: Wrong content type or a body that can't be parsed (formData()
    throws), a missing or empty field, a non-http(s) scheme, no host, or a URL
    that's too long: all give 400 with a specific message, and nothing is
    written.
  ────────────────────────────────────────
  Case: Unknown or badly shaped code
  Behavior: Wrong shape: 404 without a query. Right shape but no such row: 404.
  ────────────────────────────────────────
  Case: Migrations not applied
  Behavior: Queries fail with "no such table" and you get a 500 page. The dev
    script prevents this by applying migrations first.

  Not handled: there's no login or rate limit, so anyone who can reach the app
  can create and list links. That's fine for local use, but it matters if it's
  ever deployed.

  1. Case: Promo and promo are the same alias

  Yes, it needs a migration: 0002_case_insensitive_codes.sql adds one index,
  CREATE UNIQUE INDEX links_code_nocase ON links (code COLLATE NOCASE);.

  How it's enforced with no check before the insert:
  - The insert becomes INSERT … ON CONFLICT DO NOTHING RETURNING code, with no
    column named after ON CONFLICT. Without a named column it covers every
    uniqueness rule, including the new index.
  - If no row comes back, the alias was taken, whatever the case. D1 decides
    inside the same single statement as today.
  - I won't keep ON CONFLICT (code). With the case-insensitive index, the
    scratch run shows that form behaving in a way I wouldn't rely on.

  Stored as typed, matched in any case:
  - An alias is saved exactly as you typed it (Promo), and /promo, /PROMO and
    /Promo all redirect to it.
  - The redirect query adds COLLATE NOCASE and uses the new index (I checked the
    query plan).
  - Case folding only covers ASCII letters, which is fine because aliases are
    limited to ASCII.

  The same rule applies to generated codes. That's the only consistent choice:
  otherwise a generated Promo12 and an alias promo12 could both exist.
  - Uniqueness then drops from 62⁷ to 36⁷ ≈ 7.8×10¹⁰ possible codes, which is
    still plenty.
  - Existing mixed-case codes keep working and now also resolve when typed in
    the wrong case.

  Migration safety:
  - Applying it: it only adds an index and rewrites no data. If two existing
    codes differ only by case, creating the index fails and nothing changes. You
    can check first with SELECT lower(code), COUNT(*) FROM links GROUP BY 1 
    HAVING COUNT(*) > 1 (your local data is one row).
  - Undoing it: there are no down migrations, so it would be a new migration
    with DROP INDEX links_code_nocase plus reverting the code.
  - Order: apply the migration before running the new code. Old code running
    with the new index can't create a case duplicate; the worst case is a 500 on
    a rare collision. New code without the index would miss case duplicates.
    Locally, npm run dev and the tests apply migrations automatically.

  2. Alias format and routes

  - Format: 3–32 characters, letters, digits and -. It must start and end with a
    letter or digit. Pattern: ^[A-Za-z0-9](?:[A-Za-z0-9-]{1,30})[A-Za-z0-9]$.
  - What it excludes: no _, ., /, spaces or non-ASCII characters. So
    favicon.ico, robots.txt and anything with a dot can never be an alias.
  - Route check: the router matches its fixed routes (/, /links) first. After
    that, any path segment matching the alias pattern is looked up in the
    database; anything else is a 404 without a query. Generated codes (7
    alphanumeric characters) are a subset of that pattern.

  Reserved words:
  - The router keeps its fixed routes in one exported list. The validator
    rejects, regardless of case, every name in that list plus a small reserved
    set: api, admin, assets, static, new, cdn-cgi. cdn-cgi is reserved because
    Cloudflare uses that path.
  - How "future routes are never valid aliases" is guaranteed: a test goes
    through the router's route list and the reserved set and asserts that every
    entry fails alias validation. Adding a route to the router automatically
    makes it reserved, and the test covers it.
  - Remaining risk: an alias created before a route of the same name is added
    would be hidden by that route. Whoever adds the route then needs to check
    the database for that name. I'll put this in the README rather than build
    anything for it.
  - Generated codes: these will also skip reserved words, so a random 7-letter
    code can never match a fixed route.
